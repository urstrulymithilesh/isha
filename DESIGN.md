## Problem Statement

Build **Isha**: a personal AI companion that runs **entirely on the user's own
machine** — no cloud APIs, no cloud cost, no data leaving the device, fully
offline-capable. At the computer you talk to her by voice; she has a warm,
girlfriend-like personality; she **remembers** the user across sessions (routine,
personal facts, conversation history); and she quietly runs background timers and
timed reminders while the conversation stays live. This is a for-fun **portfolio
project** — the priority is a real, demoable v1 that the builder understands well
enough to explain in an interview, on modest hardware (GTX 1050 / 4GB VRAM), with
an architecture that lets bigger models drop in later without a rewrite.

## What Makes This Cool

- **It's fully private and offline.** No API keys, no bills, no telemetry. The
  whole "AI girlfriend that lives on your laptop and knows you" fantasy, actually
  self-hosted. Strong, unusual portfolio story.
- **She remembers you.** Persistent memory (structured facts + semantic recall)
  is the difference between "a chatbot" and "a companion." This is the demo beat
  that makes people lean in.
- **She multitasks in real time.** "Boil water for 10 minutes" runs in the
  background and she interrupts *only* when it's done — while the conversation
  never pauses. That concurrency is the signature engineering, and it explains far
  better in an interview than any framework call.
- **It's honest engineering under a real constraint.** 4GB VRAM forces genuine
  decisions (model sizing, partial offload, turn-based voice). That constraint is
  the interview story, not a weakness.

## Constraints

- **Hard: fully local, offline, zero cloud, zero cost.** Every component (LLM,
  STT, TTS, wake word, memory) self-hosted. Non-negotiable — it is the identity of
  the project.
- **Hardware:** Intel i5-8300H (4c/8t), 32GB RAM, NVIDIA GTX 1050 **4GB VRAM**
  (Pascal, no tensor cores), Intel UHD 630, Windows 11, ~1.3TB free.
- **Bottleneck is VRAM, not RAM/storage.** This caps the reasoning model size and
  makes low-latency real-time voice the hardest part.
- **Portfolio/learning bias:** prefer tools the builder can understand and explain
  over black-box magic. Working + demoable now beats architecturally ambitious.
- **Upgrade-ready:** every model/engine sits behind a clean interface so a future
  GPU upgrade is a config change (`qwen2.5:3b → qwen2.5:14b`), not a rewrite.

## Premises (agreed this session)

1. **Fully local is a fixed requirement, and its tradeoffs are accepted** — slower
   reasoning, turn-based (not full-duplex) voice in v1. Agreed.
2. **Literal phone calls are out** (PSTN/telephony = cloud). "Remote access away
   from the computer" is reframed as a phone/web client hitting the same local
   Isha over the home network (LAN or self-hosted WireGuard), and is **deferred to
   a later phase** regardless. Agreed.
3. **"Skill mastery = fine-tune to expert" is infeasible on 4GB VRAM.** Reframed as
   **on-demand RAG**: Isha ingests authoritative sources into a named knowledge
   corpus + writes herself a distilled cheat-sheet, then retrieves to guide the
   user step-by-step. "Takes time" = the background ingest job; "retained
   permanently" = the corpus persists; "forget" = delete the collection. Kept
   behind an interface so LoRA fine-tuning can slot in after a hardware upgrade.
   **Deferred past v1.** Agreed.
4. **Custom async orchestrator over LangChain** — the unique requirements
   (always-on listening, don't-interrupt-except-time-critical, live background
   timers) are about controlling an event loop, which a framework hides. Agreed.

## Recommended Approach

**v1 = Voice Companion + Memory.** Say "Isha" → wake → listen (STT) → reason
(local LLM with persistent memory + personality) → reply in voice (TTS), on an
always-on loop, plus background timers and timed reminders ("remind me at 5pm" →
local spoken announcement). Turn-based voice (not full-duplex barge-in). Defers
skill-mastery, remote access, and proactive daily learning to later phases.

Chosen because it delivers the emotional core of the concept — *talk to her, she
remembers, she's there* — is the version that actually lands in a portfolio demo,
and sidesteps the two biggest rabbit holes (telephony, fine-tuning).

### Recommended stack (all free / open-source / local)

| Layer | Choice | Why | Later swap |
|---|---|---|---|
| Reasoning | **Ollama** running **Qwen2.5-3B-Instruct** (Q4) | Clean HTTP API, model swap = 1 line; 3B fits ~2GB VRAM, snappy; strong instruction-following + tool calls | llama.cpp server for internals; 7B/14B on GPU upgrade |
| STT | **faster-whisper** (CTranslate2, **CPU int8**), `base.en`/`small.en` | Runs on CPU so the GPU stays dedicated to the LLM; int8 is fast enough for short utterances on the i5 | `large-v3` / GPU after upgrade |
| TTS | **Piper** (binary release, not the flaky pip pkg; pulls `espeak-ng` DLL) | Fast, **CPU-only** (leaves VRAM for the LLM), warm voices, tiny | Higher-quality local TTS / voice clone later |
| Wake word | **openWakeWord** (ONNX) + **Silero VAD** | Fully open, lightweight always-on. NOTE: no stock "Isha" model — ship a stock word in Phase 0, train custom "Isha" in Phase 4 | — |
| Memory | **SQLite** (stdlib `sqlite3` 3.45.3 — VERIFIED it loads extensions on this Python 3.13) + **sqlite-vec** | Single portable file, no server; embeddings from a **CPU** sentence-embedder (bge-small via fastembed), NOT a GPU model | LanceDB/Chroma if scale grows |
| Orchestrator | **Custom `asyncio` event loop** (Python 3.11) | Full control of turn-taking, interrupt policy, background jobs; best interview material | — |
| Scheduler | asyncio + **SQLite-persisted** jobs (absolute wall-clock fire times) | Timers, "call me at X"; survives crash/restart/sleep via reconcile-on-resume | — |

**Compute split (locked in eng review):** GPU = reasoning only (Qwen pinned
resident, `keep_alive=-1`, KV/context **capped** so Windows' reserved VRAM
doesn't OOM the 4GB). CPU = hear (faster-whisper int8) + speak (Piper) +
embeddings. No two models ever contend for the 4GB.

**OS note:** everything runs native on Windows 11 (Ollama, faster-whisper CPU,
Piper binary, openWakeWord ONNX). WSL2 with GPU passthrough is an option for
smoother Linux tooling but adds complexity — start native Windows.

## Architecture (interfaces first — upgrade = swap impl, not rewrite)

```
  Voice I/O          Reasoning           Memory              Skills/Tools
  ─────────          ─────────           ──────              ────────────
  WakeWord      ┐    LLM (interface)  ┐  MemoryStore     ┐   ToolRegistry
  Transcriber   ├──► Ollama impl      ├─►SQLite+sqlite-vec├─► timer, reminder,
  Synthesizer   ┘    (swap=config)    ┘  Embedder(iface) ┘   note, (skill-RAG)
       │                   │                    │                  │
       └───────────────────┴──── Orchestrator (asyncio) ──────────┘
                     always-on loop · turn-taking · interrupt policy
                     Scheduler: timers · timed reminders · (daily ingest)
```

Core interfaces to define first: `AudioTransport`, `WakeWord`, `Transcriber`,
`Synthesizer`, `LLM`, `MemoryStore`, `Embedder`, `Tool`. Each has exactly one v1
implementation; the value is that v2 swaps the impl behind the same signature.

**Interface-design rule (eng review):** define each interface by a **minimal
capability contract**, never a vendor's wire format. `LLM` =
`chat(messages, *, stream) -> token iterator` + a `supports_tools` flag — NOT
Ollama's HTTP request/response shape (or swapping to a raw llama.cpp server
becomes a rewrite). `Transcriber` = bytes → text. `Synthesizer` = text → audio
frames. `AudioTransport` = the mic/speaker boundary; the v1 impl is local
WASAPI in/out, and the rejected VoIP idea (see Finding 1) becomes a clean
drop-in adapter here if remote access ever justifies relaxing the privacy line.

## Approaches Considered

### Approach A: Brain first, voice later — *(not chosen)*
Text companion (LLM + memory + tools) first, add voice in phase 2. Lower risk but
less flashy early, and the user prioritized the demoable voice experience.

### Approach B: Voice Companion + Memory — **CHOSEN**
The recommended approach above. Best balance of "wow" and buildability; defers the
two rabbit holes.

### Approach C: Voice Companion + Skill Mastery — *(deferred to v2)*
B plus the signature RAG skill-mastery feature. Most unique, but too much
integration risk for a first runnable version. Becomes the v2 headline feature.

## Success Criteria (v1 "done")

1. Say the wake word (a **stock** openWakeWord word in Phases 0-3; the custom
   "Isha" word lands in Phase 4) → she wakes and responds by voice, hands-free.
2. A full turn (wake → STT → LLM → TTS) completes in a **conversational** window
   (target ≈2–5s on this hardware; measure and tune, don't chase sub-second).
3. Tell her a fact today ("my sister's name is Anya"); she **recalls it correctly
   in a new session tomorrow**.
4. "Set a 10-minute timer" → conversation continues normally → she interrupts to
   announce it **exactly when it fires**, then resumes.
5. "Remind me at 5pm to go to the gym" → she announces it by voice at 5pm.
6. Personality is consistently warm/companion-like across turns (system prompt +
   persona file), not a generic assistant tone.
7. Runs with **no network connection** — provable by pulling the ethernet/wifi.

## Distribution Plan

It's a personal local app, so "distribution" = it runs on the builder's machine.
For the **portfolio** value, treat distribution as: a public **GitHub repo** with a
clear README (architecture diagram, the 4GB-VRAM constraint story, setup steps), a
**short demo video/GIF** (the memory + timer beats), and a one-command local setup
(`ollama pull ...` + `pip install -r requirements.txt` + `python -m isha`). No app
store, no CI/CD needed for v1; add a GitHub Actions lint/test check as polish.

| # | Decision | Rationale |

VoIP survives as a future adapter behind the interface. |
| 2 | **Compute: GPU=reason, CPU=hear+speak+embed** | STT (faster-whisper int8), TTS (Piper), embeddings all on CPU; Qwen pinned resident on GPU (`keep_alive=-1`, capped KV). No two models contend for the 4GB. |
| 3 | **Memory: async idle-gap extraction + strict read budget** | Fact extraction runs in the idle gap after a reply (never concurrent with the next turn — same Qwen would serialize and spike latency). | 4 | **Scheduling: SQLite-persisted, wall-clock, reconcile-on-resume** | Absolute fire times survive crash/restart/sleep; overdue events fire late with an honest "due N min ago" note; stale ones dropped. |
| 5 | **Interfaces by capability contract, not vendor wire format** | Protects the "swap = config" guarantee. |
| 6 | **Barge-in: stop-word live during speech** | Full STT gated while she speaks, but the wake/stop-word detector stays live so voice can cut her off at a sentence boundary. Headset prevents self-trigger. |

## Preemption state machine (the "signature" concurrency model — specify it explicitly)

```
        wake word            VAD endpoint           reply ready
  IDLE ───────────► LISTENING ───────────► THINKING ───────────► SPEAKING
   ▲                    │  (full STT open)     │ (Qwen on GPU)      │ (Piper + stop-word live)
   │                    │                      │                    │
   │  reply done /      │                      │                    │  stop-word / reply done
   └────────────────────┴──────────────────────┴────────────────────┘

  PENDING-ALERT (timer/reminder fires) — priority overlay on any state:
    • fires while IDLE/SPEAKING      → speak immediately (she owns the speaker)
    • fires while user is LISTENING  → WAIT for VAD endpoint, then speak
                                       (concept rule: don't interrupt the user
                                        unless time-critical; timers/reminders
                                        count as time-critical → interject at the
                                        next silence, not mid-word)
    • fires while THINKING           → queue, speak after the reply
  Half-duplex invariant: entering SPEAKING mutes full STT AND flushes the mic
  buffer on exit (kills self-trigger echo). Stop-word detector is the only live
  input during SPEAKING.
```

## Test strategy (was absent — now required in-plan)

Deterministic core = 100% unit (fake clocks, known corpora). Pipeline = integration
with mocked audio/LLM. Persona/recall = eval, re-run on every model swap.

- **MemoryStore** [unit, P1]: upsert/dedupe, semantic recall top-K, read-budget cap, conflict last-write-wins, malformed-JSON rejection.
- **Scheduler** [unit, P1]: fires once at wall-clock time (fake clock); persist+reload; **overdue-reconcile on resume** (clock jump → fires late w/ note) — regression-class.
- **Orchestrator/preemption** [integration, P1]: timer fires mid-generation → alert preempts correctly per state; entering SPEAKING gates full STT + flushes buffer (no self-wake); stop-word interrupts at sentence boundary.
- **Pipeline glue** [integration, P1]: feed a WAV, mock LLM → assert TTS called with the reply.
- **Persona/LLM** [→EVAL, P2]: 10-prompt regression — warmth held + a stored fact recalled; keep Llama-3.2-3B as a drop-in A/B behind `LLM`.

## Seeded memory (core + self facts) — added post-Phase-2

Beyond conversationally-learned facts, the store holds **seeded** facts with a protected
`origin` (`isha/memory/seed.py`, applied via `python -m isha seed`, auto-seeded first run):
- **core** — identity + relationship (her name Isha, his name Mithilesh, that he created
  her, the intended partner relationship, that she's his best creation). Conversational
  extraction can NEVER overwrite these (an offhand remark can't rewrite her identity).
- **self** — her current build (version, abilities, intro, tech stack); recalled normally.
- **self_history** — past-version facts; hidden from normal recall, surfaced only when the
  user asks about her past (`_asks_about_past`), so she can tease about her progress.
